Рекомендации по развитию

Приоритизированный список улучшений, основанный на архитектуре и текущем MVP платформы.

P0 · Before public launch

1. Проверяемый запуск и интеграционные тесты

Настроить CI на Node.js 20/22 и выполнять тесты не только синтаксиса, но и настоящего PostgreSQL/Data API/HTTP через Docker Compose.

  • Автоматизировать ZIP → draft → private test → publish → catalog.
  • Проверить запрет доступа к draft HTML и каждому draft asset для гостя и игрока.
  • Покрыть CSRF, Origin, OAuth state, email OTP, неправильные типы файлов, traversal и лимиты ZIP.
P0 · Trust & safety

2. Разделить пользовательские игры и домен платформы

Для production отдавать произвольные игры с отдельного origin, запретить опасные MIME-типы, сканировать загружаемые архивы и регулярно обновлять sandbox/container runtime. Подготовить политику конфиденциальности, условия и процесс модерации.

P1 · Reliability

3. Очередь фоновых задач и восстановление

Вынести запуск/остановку server runtime, проверку архивов, отправку почты и очистку старых данных в управляемые фоновые задачи. Добавить резервные копии PostgreSQL и storage-volume, регулярные тесты восстановления, health checks Data API/Platform API, структурированные логи и уведомления об ошибках контейнеров.

P1 · Analytics

4. Целостность метрик и прозрачность очков

Установить срок хранения сырых событий, idempotency для сессий и событии share/favourite, дедупликацию ботов и аудит скачков активности. Текущие очки — игровые баллы, а не средство выплат; формулу и правила начисления нужно показывать игрокам.

P1 · Multiplayer

5. Надёжность многопользовательских сессий

Для сетевых игр определить состояние комнаты и правила переподключения, heartbeat игрока, timeout/AFK, versioned messages и серверное подтверждение каждого хода. Не хранить единственный источник истины в localStorage или браузере игрока.

P2 · UX

6. Проверить пользовательские сценарии и доступность

Провести мобильные usability-тесты каталога, карточки игры, оценок, настроек профиля и попапов. Проверить клавиатурную навигацию, focus trap для модальных окон, контраст тем, reduced motion, медленную сеть и локализацию русских/английских длинных строк.

P2 · Scale

7. Подготовить архитектуру к росту

PostgreSQL и внутренний Data API уже выделены в отдельные сервисы; не публиковать Data API наружу. Следующие приоритеты: вынести игровые ZIP/аватары/капсулы в S3/GCS, выделить Docker runtime в отдельный ограниченный runtime-manager, добавить миграции схемы с версиями и checksum, восстановление из backup, централизованные логи/алерты и worker для тяжёлой аналитики. Для горизонтального масштабирования Platform API обеспечить shared storage, CDN/WAF и сетевую защиту L3/L4; Express rate limit сам по себе не является DDoS-защитой.

P0 · API contract

8. Держать API-документацию синхронной с кодом

На странице документации появилась отдельная вкладка API с публичными, пользовательскими, SDK и административными маршрутами и примерами fetch/curl. Следующий шаг — определить OpenAPI 3.1 как машиночитаемый источник истины и проверять схемы request/response в CI.

  • Требовать session cookie и CSRF для изменяющих запросов, а ADMIN для административных операций.
  • Добавить версионирование публичного SDK, совместимые изменения и contract tests для маршрутов.
  • Не возвращать email, внутренние ID/ошибки Data API или secrets публичным клиентам.
P1 · Operations

9. Персистентные логи и мониторинг

Dashboard показывает доступные ошибки приложения и runtime-состояние; ошибки в памяти теряются при рестарте. Для production нужно логирование JSON в stdout + централизованный сбор, correlation/request IDs, retention, алерты для crash-loop, недоступного Data API, долгих запросов и ошибок Docker runtime. Не отдавать необработанные stacks и секреты пользователям панели.

P1 · UX & accessibility

10. Регрессионные тесты dashboard и интеракций

Проверять двухколоночную сетку на landscape, touch/pen reorder, сохранение пользовательского порядка, tab/keyboard accessibility, tooltip/aria labels, восстановление скрытых widgets, правильную локализацию и отсутствие theme flash на каждом маршруте. Критичные сценарии проверять в настоящем браузере, а не только через статический тест.

P0 · Product governance

11. Измерять продуктовые результаты, а не только события

Для ключевых сценариев задавать целевую метрику и критерий готовности: открытие карточки → запуск игры → активная сессия → возврат; upload → private test → publish; тикет → первый ответ → решение. У каждого дашборда должны быть определение показателя, окно времени, источник и известные ограничения данных. Не сравнивать CCU, уникальных игроков за день и число запусков как взаимозаменяемые метрики.

  • Фиксировать события схемой с версией, request/correlation ID и UTC timestamp.
  • Проводить аудит качества аналитики после каждого изменения SDK и API.
  • Разделять технические SLI (ошибки, latency, доступность) и продуктовые KPI (активация, повторная игра, завершение сессии).
P1 · Dashboard UX

12. Сохранить управляемый рабочий стол администратора

У виджетов должны быть предсказуемые варианты: стандартная карточка, расширенная сеточная ширина и подробный полноэкранный просмотр. Перетаскивание не должно мешать таблицам и формам; для touch нужны выделенная ручка, видимый drop target и анимация FLIP. Состояние сетки хранить по версии схемы, чтобы обновления могли мигрировать устаревшие layout-предпочтения.

P1 · Scoring transparency

13. Документировать начисление очков однозначно

Показывать игрокам формулу игрового рейтинга и её актуальную серверную реализацию. Базовое начисление за время рассчитывается по подтверждённым активным секундам; бонусы за отзывы, избранное и первый share каждой игры должны быть идемпотентными. Дубли событий не должны увеличивать результат. Изменение правил требует обновления UI-текста, серверного кода и тестов одним релизом.
