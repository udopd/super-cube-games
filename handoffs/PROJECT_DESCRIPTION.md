# Описание проекта — SUPER CUBE Games Platform

## Идея

SUPER CUBE Games — платформа для запуска веб-игр прямо в браузере. Сейчас проект задуман для одного администратора, который загружает ZIP-архив, проверяет игру на закрытой тестовой странице, правит карточку и публикует её в общем каталоге. Игроки авторизуются через Яндекс ID, Google или email-код, ведут историю игр, добавляют игры в избранное, оценивают их, оставляют несколько комментариев на игру, делятся ссылками и синхронизируют облачные сохранения. Для игры доступен browser iframe runtime или изолированный Docker server runtime.

## Ключевые роли

### Администратор

- Один административный аккаунт определяется значением `ADMIN_EMAIL` в `.env`.
- Загружает ZIP через drag-and-drop или файловый диалог.
- Получает автоматически разобранные название, описание, теги и обложку из архива.
- Открывает приватную сборку по адресу `/games/<slug>-test`.
- Может редактировать название, краткое описание, теги, диапазон числа игроков и обложку.
- Публикует игру по `/games/<slug>` или снимает с публикации.
- Просматривает статистику каталога и каждой игры: уникальные игроки, сессии, рейтинг, оценки, медиана времени игры, отзывы, клики, переходы из каталога/с внешних ресурсов, избранное.

### Игрок

- Входит через приоритетный Яндекс ID, Google или email-код.
- Может играть без аккаунта; анонимная статистика определяется локальным случайным ID браузера.
- Авторизованный игрок может сохранять состояние игры в облаке, выставлять оценку, писать/редактировать свой отзыв, добавлять/убирать игру из избранного.
- В профиле есть «Все игры», «Недавние игры» (последние пять), «Мои избранные» и топ-3 игр по суммарному времени.

## Структура игрового ZIP

```text
my-game.zip
├── index.html
├── runtime.txt                # optional: browser / server
├── media/
│   ├── title.txt              # English-only title
│   ├── description.ru.txt
│   ├── description.en.txt
│   ├── tags.ru.txt
│   ├── tags.en.txt             # catalog filters always use English tags
│   ├── capsule.jpg             # exactly 630×500 px
│   ├── promo.png
│   └── screenshots/
│       ├── 01.jpg
│       └── 02.webp
└── server/                    # required for runtime=server
    └── index.js
```

Все пять metadata-файлов должны лежать в папке `media/`. Текстовые файлы — UTF-8. Новые игры обязаны предоставлять RU/EN описание и теги; backend читает старые `description.txt` и `tags.txt` только ради обратной совместимости, новые архивы должны использовать только каноническую структуру. Название из `title.txt` всегда английское. Дополнительные картинки прямо в `media/` используются как промоматериалы, а `media/screenshots/` — как скриншоты попапа. Лимиты и проверки описаны в `README.md`. Пример серверной игры: `examples/durak-online.zip` (2–6 игроков, серверная проверка карт/ходов, polling-based rooms).

## Авторизация и безопасность

- Административный вход использует `ADMIN_LOGIN` и `ADMIN_PASSWORD`; email роли администратора задаётся через `ADMIN_EMAIL`.
- Вход игроков выполняется по email-коду через SMTP; сохраняется только hash кода, срок действия 10 минут, максимум пять попыток проверки.
- Все изменяющие API-запросы защищены CSRF-токеном и проверкой Origin; есть rate limits и базовые security headers.
- ZIP проверяется до и во время распаковки: размер, общий распакованный размер, количество файлов, traversal, абсолютные пути, symlink и compression ratio.
- Пользовательские игры запускаются в `iframe sandbox` без `allow-same-origin`. Для тестовой сборки сервер выдаёт краткоживущий HttpOnly cookie с подписанным доступом к файлам только конкретного черновика.
- Rate limit на уровне Node.js не заменяет сетевую DDoS-защиту: production должен находиться за CDN/WAF и защитой хостинга.

## SDK

Сервер добавляет `/js/game-sdk.js` в HTML-страницу игры. Игра вызывает `window.SuperCubePlatform`:

- `getUser()` — узнать, есть ли авторизованный аккаунт (не возвращает email/админские данные в iframe).
- `save(data)` / `loadSave()` — облачное сохранение, доступное авторизованному игроку.
- `rate(1…5)` — оценка.
- `review(text)` — новый комментарий; допускается несколько комментариев к игре, а очки берутся по самому длинному.
- `favorite()` — переключить избранное.
- `share()` — записать факт «Поделиться» и получить URL игры.
- `recordClick(label)` — измерить важное действие/клик.
- `track('custom_click' | 'level_start' | 'level_complete', metadata)` — игровое событие аналитики.

SDK не даёт коду игры прямой доступ к cookie или сессии платформы. Запросы проходят через `postMessage` host-страницы, а backend ещё раз проверяет авторизацию и допустимые данные.

## Статистика

- Уникальные игроки — число уникальных аккаунтов плюс анонимные browser IDs, встречавшиеся в игровых сессиях.
- Запуски и продолжительность — из таблицы игровых сессий; медиана рассчитывается сервером по фактическим duration.
- Рейтинг — среднее по текущим оценкам уникальных авторизованных пользователей; у пользователя одна актуальная оценка для одной игры.
- Отзывы — несколько комментариев на одну игру; автор редактирует только свои, администратор может удалить любой комментарий и ответить на него.
- События — клики внутри игры, игровые события, переходы из каталога, внешние открытия, события избранного.
- Сохранения — JSON до 250 KB на пользователя/игру.

## Дашборды, профиль и топ игроков

- `/documentation.html` содержит проектную архитектуру и встроенный двуязычный справочник SDK с промптами для создания новой игры и адаптации существующего ZIP; `/sdk.html` перенаправляет на этот раздел.
- `/admin/metrics` — отдельный админский дашборд по общеплатформенным метрикам и очкам, деталям игроков и отправке письма из шаблона.
- Публичный `/leaderboard.html` показывает только `SC-…` ID, никнейм и очки. Игрок может поменять никнейм, загрузить квадратный аватар 512×512 и настроить пароль.
- Очки серверного рейтинга зависят от активного игрового времени, самого длинного отзыва на игру, однократного добавления каждой игры в избранное, share по игре и суммарных часов. Heartbeats ограничены короткими интервалами; это защита от случайного background time, но не абсолютная антибот-защита.
- Герой (`/hero.html`) отделён от каталога (`/`) и не использует вводящий в заблуждение контейнер заголовка каталога.

## Server runtime

`runtime.txt=server` вместе с `server/index.js` включает отдельный Docker-контейнер с ограничениями CPU/RAM/PID, read-only файловой системой, dropped capabilities, no-new-privileges и внутренней сетью без внешнего доступа. Точка входа слушает `0.0.0.0:3000`. Docker CLI и Docker Engine socket доступны только выделенному доверенному сервису `game-runtime`; Platform API общается с ним через внутренний token-authenticated HTTP API. Контейнер игры получает read-only копию только своей папки, не весь volume платформы. Память процесса не персистентна: сетевые игры должны сохранять важное состояние через платформенный API/хранилище, если нужна непрерывность после перезапуска.

## Исторические метрики и runtime

Снимки CCU и истории дневных игроков записываются сервером каждую минуту. Графики честно показывают только период после установки этой версии, без искусственного восстановления несуществующей истории. Серверные игры используют отдельный Docker-контейнер с `0.0.0.0:3000` внутри и уникальным loopback-портом снаружи; опубликованные серверные игры прогреваются при запуске приложения. `/api/games/:slug/ping` возвращает статус и задержку. Runtime требует Docker Engine и доступного образа.

## SEO

Каталог имеет title, description, keywords как начальную семантическую подсказку, canonical, Open Graph, JSON-LD `WebSite`; страницы опубликованных игр получают уникальные title/description, canonical, Open Graph и JSON-LD `VideoGame`. `robots.txt` закрывает из индекса приватные профили, админку и тестовые URL; `sitemap.xml` генерируется по опубликованным играм.

Ключевые смысловые запросы для контента: «браузерные игры», «онлайн игры бесплатно», «игры без скачивания», «мини игры», «HTML5 игры», «головоломки онлайн», «аркады», «казуальные игры», «инди игры в браузере». В production нужно заменить базовое доменное имя, добавить реальные тексты/категории и подключить панели вебмастеров; сами keywords в meta не гарантируют ранжирование.

## Архитектура данных и границы сервисов

Platform API (`server.js`) содержит пользовательские маршруты и бизнес-правила, но не подключается к СУБД напрямую. Его `src/db.js` отдаёт клиент `shared/data-client.js`, который отправляет в Data API только SHA-256 ID SQL-оператора, режим и параметры. Data API (`data-service/server.js`) сверяет ID с `data-service/query-catalog.json`, проверяет число параметров и исполняет только статически зарегистрированный SQL через `pg`. Произвольный SQL-код по HTTP не принимается. Межсервисные запросы закрыты общим `DATA_API_TOKEN`; в Docker Compose Data API доступен только внутри сети Compose.

PostgreSQL 16 хранит аккаунты, email identities, игры и публикации, игровые сессии, события, оценки, отзывы, избранное, облачные сохранения, OTP и серверные сессии Express. Пакетный endpoint Data API исполняет группу операций в транзакции PostgreSQL. Снимки CCU и ежедневных метрик сохраняются в `metric_snapshots`.

```text
Browser / Game SDK → Platform API (Express) → private Data API → PostgreSQL
                                                  └→ shared persistent file volume (current)
```

`docker-compose.yml` поднимает PostgreSQL, Data API и Platform API отдельно. `Dockerfile` собирает Platform API-образ без пакета `pg`, а `Dockerfile.data-api` — минимальный образ только с Express, `pg` и компонентами Data API; Compose не передаёт `DATABASE_URL` или пароль БД в Platform API. `Platform API` ждёт health-check Data API на старте. Для переноса данных из старой SQLite существуют `scripts/export-sqlite.py` и `scripts/import-sqlite-export.mjs`. Внимание: игровые файлы и аватары пока хранятся в постоянном volume, а не в GCS/S3; перевод на объектное хранилище запланирован отдельным этапом.

## Технологии

- Node.js + Express для Platform API и Data API
- PostgreSQL 16 через `pg` — единственный драйвер базы установлен в Data API
- Private Data API: SHA-256 allowlist, параметризация, межсервисный Bearer token, транзакционные batches
- Express session store в PostgreSQL (`app_sessions`)
- SMTP через Nodemailer
- Multer + streaming ZIP extraction (`yauzl`)
- Image dimension validation (`image-size`)
- Vanilla HTML/CSS/JS; без фронтенд-фреймворка

## Email login and canonical game identity

Email authentication has separate sign-in and registration modes. Email codes are bound to the selected flow; requesting a new code replaces the active OTP challenge and resets its failed-attempt counter without deleting the player account. Existing provider identities are reused only for the account that owns them. The game player uses the canonical route slug and strips source attribution such as `src=catalog` from the visible URL; source tracking does not affect game identity or cloud-save keys.

## Продуктовая архитектура и модель эксплуатации (vNext)

### Миссия

Создать понятное место для поиска, запуска и повторного прохождения небольших браузерных игр и одновременно дать независимому разработчику безопасный, измеримый процесс публикации. Ключевые продуктовые свойства — короткий путь до игры, непрерывность прогресса, прозрачная публичная идентичность игрока и стабильный контракт интеграции для разработчиков.

### Архитектурные решения как продуктовые гарантии

- **Идентичность игры стабильна.** Используется ID записи и slug, а не ZIP-версия и не query string. `?src=catalog` фиксирует источник перехода и не влияет на облачное сохранение.
- **Загрузка отделена от выпуска.** ZIP сначала становится черновиком, проходит валидацию и тест, затем публикуется. Обновление архива сохраняет исходную запись игры, рейтинги, отзывы, сохранения и аналитику.
- **Недоверенный клиент.** Браузерная игра работает внутри sandboxed iframe без `allow-same-origin`. SDK — узкий интерфейс разрешённых действий, но не источник истины для идентичности, результата игры или очков.
- **Изолированный серверный запуск.** Игры с серверным состоянием запускаются отдельным runtime manager с ограниченными ресурсами и сетевыми правами. Docker socket не передаётся Platform API.
- **Разделение бизнес-логики и хранения.** Platform API отвечает за правила; Data API выполняет только allowlisted PostgreSQL-операции. Секреты соединения с БД не передаются в браузер и контейнер Platform API.
- **Единая таксономия тегов.** Теги нормализуются в нижний регистр, чтобы фильтры не дублировались из-за регистра. Название игры хранится на английском, описания и теги имеют RU/EN версии.

### Ответственность компонентов

- **Platform API:** аутентификация и права, каталог, публикация/обновление игр, правила начисления очков, профиль, SDK bridge, заявки поддержки и публичный HTTP-контракт.
- **Data API:** параметризованные SQL-операции по allowlist, транзакционные границы, схема PostgreSQL и управляемые миграции.
- **PostgreSQL:** долговечные записи пользователей, игр, сессий, событий, отзывов, оценок, сохранений и метрик.
- **Файловое хранилище:** ZIP-архивы, распакованные релизы и медиа. В текущей версии используется постоянный volume; переход на объектное хранилище — отдельный этап.
- **Game runtime manager:** запуск, остановка и проксирование серверных игр. Доступ к Docker Engine привилегированный и должен оставаться во внутреннем сервисе.
- **Игровой SDK:** совместимый фасад для игровых функций, который не открывает игру к приватной сессии платформы напрямую.

### Качество и приёмка релизов

Каждое изменение пользовательского сценария должно иметь критерий готовности, RU/EN тексты, проверку desktop/mobile, клавиатуры и reduced motion, регрессионный тест и обновление документации при изменении контракта. Статические проверки необходимы, но не заменяют smoke-тесты с настоящими PostgreSQL, Docker и браузером. Для production обязательны упражнения по восстановлению backup, централизованные структурированные логи, алерты, edge rate limits, правила конфиденциальности/условия и проверяемый rollback.

### Аналитика и очки

CCU, дневные уникальные игроки, число сессий, медиана длительности и рейтинг — разные показатели с разными определениями. Очки считаются сервером: активные минуты, бонус за полный накопленный час, оценка самого длинного отзыва по каждой игре, первое добавление каждой игры в избранное и первое подтверждённое поделиться каждой игрой. Повторные события должны быть идемпотентными. Текст интерфейса и тесты синхронизируются с серверной формулой.
