SUPER CUBE Games Platform — handoff summary
Updated: 2026-10-11

Purpose
Self-hosted browser-game platform: public catalogue, one administrator, ZIP upload, private draft/testing, publishing, player accounts, ratings/reviews/favorites/cloud saves, game SDK, public player leaderboard, admin metrics and isolated server-game runtime via dedicated `game-runtime` service (only that service mounts Docker socket; Platform API uses token-authenticated internal HTTP).

Current stack and architecture
- Node.js >=20, Express 4, vanilla HTML/CSS/JS.
- Platform API: server.js, port 3000. Business logic and permissions stay here; it has no PostgreSQL driver.
- Internal Data API: data-service/server.js, default port 4001. Only this service imports pg and accesses PostgreSQL.
- Data API calls use SHA-256 statement IDs, request mode and bound parameters. SQL is allowlisted in data-service/query-catalog.json; arbitrary SQL text is never accepted over HTTP. Internal calls require DATA_API_TOKEN. /internal/v1/batch executes up to 100 statements in a PostgreSQL transaction.
- PostgreSQL 16 schema: data-service/schema.sql, tables users, identities, games, play_sessions, game_events, ratings, reviews, favorites, cloud_saves, email_codes, metric_snapshots, app_sessions.
- shared/data-client.js implements the Platform API client; shared/data-api-session-store.js backs Express sessions in PostgreSQL.
- docker-compose.yml runs postgres, private data-api, and platform. Data API has no host port. PostgreSQL is mapped only to 127.0.0.1 for local migration tools. Platform does not receive DATABASE_URL / PostgreSQL credentials in Compose. Dockerfile builds the Platform API without pg; Dockerfile.data-api builds the minimal Data API image with pg.
- Uploaded games, avatars and media still use the persistent platform-storage volume. S3/GCS object-storage adapter is not implemented yet. Docker game runtime still runs from the Platform API process; a separate restricted runtime-manager is a production follow-up.

Useful files

Start
1. cp .env.example .env
2. Set SESSION_SECRET, OTP_PEPPER, DATA_API_TOKEN (at least 32 random characters), POSTGRES_PASSWORD and ADMIN_EMAIL.
3. docker compose up --build
4. Open http://localhost:3000/; health-check is http://localhost:3000/health.

To start processes outside Compose, start PostgreSQL, set DATABASE_URL to localhost, run npm install, then run npm run start:data and npm start in separate terminals. Platform API waits for Data API health. Do not expose Data API publicly. Never commit .env or migration exports.

SQLite migration
1. Stop writes to the legacy platform.
2. python scripts/export-sqlite.py storage/platform.sqlite migration-export.json
3. Start PostgreSQL / Data API and run node scripts/import-sqlite-export.mjs migration-export.json with DATABASE_URL targeting the reachable PostgreSQL host.
4. Compare row counts and metrics before switching; remove the JSON export safely. Sessions are intentionally not migrated, so players may need to sign in again.

Compose includes a dedicated `game-runtime` service (`Dockerfile.runtime`, `runtime-service/server.js`) that owns Docker CLI/socket and offers a token-protected internal API. Add `SERVER_GAME_RUNTIME_TOKEN` to the existing `.env` before upgrading; keep the existing PostgreSQL and platform-storage volumes. Run `docker compose up -d --build game-runtime platform` and verify with `docker compose exec game-runtime docker info`. `npm test` passes, but Docker Desktop socket behavior needs live testing.

Runtime diagnostic fix: game ZIP files are written mode 0640 but isolated game containers run as UID 10001. The runtime manager now chmods only the per-game copy to a+rX, captures logs before failed-container cleanup, and propagates development diagnostics through Platform API. `npm test` passes; Docker Engine integration still needs running Docker Desktop. Rebuild/recreate only game-runtime and platform; do not delete volumes.
